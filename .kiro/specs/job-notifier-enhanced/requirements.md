# Requirements Document

## Introduction

Доработка проекта job-notifier на Rust. Проект представляет собой скрейпер вакансий, который периодически обходит указанные URL и уведомляет пользователя о новых вакансиях, соответствующих фильтрам.

Планируется две крупные доработки:

1. **Универсальный скрейпер** — вместо отдельного скрейпера под каждый сайт, единый механизм, который обходит HTML-страницу по всем div-элементам и ищет совпадения с ключевыми словами/фильтрами пользователя.

2. **Трекер заявок (Job Application Tracker)** — таблица для отслеживания статуса поданных заявок с уведомлениями об истечении срока ожидания ответа.

## Glossary

- **Universal_Scraper**: универсальный скрейпер, который извлекает вакансии с произвольных HTML-страниц без сайт-специфичной логики.
- **Job**: структура данных, описывающая вакансию (компания, должность, URL, стек, грейд, зарплата).
- **Application**: запись о поданной заявке на вакансию (компания, позиция, дата подачи, срок ожидания, статус).
- **Application_Tracker**: компонент для хранения и управления записями о поданных заявках.
- **Notifier**: компонент, отправляющий уведомления пользователю (консоль, Telegram и т.д.).
- **Filter**: набор условий (ключевые слова, грейд, технологии), по которым отбираются вакансии.
- **Storage**: компонент для персистентного хранения данных в SQLite.
- **Scheduler**: компонент, запускающий скрейпинг и проверку дедлайнов по расписанию.
- **Deadline**: дата, после которой считается, что компания не ответила на заявку.
- **ApplicationStatus**: статус заявки: `Submitted`, `InReview`, `Rejected`, `OfferReceived`, `Withdrawn`.

## Requirements

### Requirement 1: Универсальный скрейпер HTML-страниц

**User Story:** Как пользователь, я хочу добавлять произвольные URL в конфиг и получать вакансии с любого сайта, чтобы не писать отдельный скрейпер под каждый ресурс.

#### Acceptance Criteria

1. THE Universal_Scraper SHALL принимать URL и возвращать список объектов `Job`, извлечённых из HTML-страницы по этому URL.
2. WHEN Universal_Scraper обходит HTML-страницу, THE Universal_Scraper SHALL проверять текстовое содержимое каждого `div`-элемента на совпадение хотя бы с одним ключевым словом из конфига.
3. WHEN текстовое содержимое `div`-элемента содержит хотя бы одно ключевое слово из конфига, THE Universal_Scraper SHALL извлекать из этого элемента поля: заголовок вакансии, название компании и URL вакансии.
4. WHEN URL вакансии является относительным путём, THE Universal_Scraper SHALL преобразовывать его в абсолютный URL на основе базового URL страницы.
5. IF HTTP-запрос к URL завершился с ошибкой, THEN THE Universal_Scraper SHALL возвращать ошибку типа `ScraperError::Network` с указанием URL и причины.
6. IF HTML-страница не содержит ни одного `div`-элемента, совпадающего с ключевыми словами, THEN THE Universal_Scraper SHALL возвращать пустой список без ошибки.
7. THE Universal_Scraper SHALL реализовывать трейт `Scraper` и быть совместимым с существующим `JobScheduler`.
8. THE Universal_Scraper SHALL извлекать грейд вакансии из заголовка, используя существующую логику `detect_grade`.
9. WHERE в конфиге указан `user_agent`, THE Universal_Scraper SHALL устанавливать заголовок `User-Agent` при HTTP-запросах.

### Requirement 2: Конфигурация универсального скрейпера

**User Story:** Как пользователь, я хочу задавать ключевые слова для поиска вакансий в файле `Config.toml`, чтобы управлять фильтрацией без перекомпиляции.

#### Acceptance Criteria

1. THE AppConfig SHALL поддерживать поле `keywords` типа `Vec<String>` в секции `[scraping]` файла `Config.toml`.
2. WHEN файл `Config.toml` не содержит поля `keywords`, THE AppConfig SHALL использовать пустой список по умолчанию.
3. THE AppConfig SHALL передавать список `keywords` в `Universal_Scraper` при инициализации.
4. IF поле `keywords` присутствует в конфиге и не является пустым списком, THEN THE Universal_Scraper SHALL использовать эти ключевые слова для фильтрации `div`-элементов.
5. WHERE в конфиге указан `user_agent`, THE AppConfig SHALL передавать его значение в `Universal_Scraper`.

### Requirement 3: Хранение заявок в базе данных

**User Story:** Как пользователь, я хочу сохранять информацию о поданных заявках в базе данных, чтобы отслеживать их статус.

#### Acceptance Criteria

1. THE Storage SHALL поддерживать операцию создания записи `Application` с полями: `id`, `company`, `position`, `applied_at` (дата подачи), `expected_reply_days` (срок ожидания в днях, по умолчанию 21), `status` (`ApplicationStatus`), `notes` (опциональный текст).
2. THE Storage SHALL поддерживать операцию получения всех записей `Application`, отсортированных по `applied_at` по убыванию.
3. THE Storage SHALL поддерживать операцию обновления поля `status` записи `Application` по её `id`.
4. THE Storage SHALL поддерживать операцию удаления записи `Application` по её `id`.
5. THE Storage SHALL поддерживать операцию получения всех записей `Application`, у которых дата дедлайна (`applied_at + expected_reply_days`) равна текущей дате и статус равен `Submitted` или `InReview`.
6. IF запись `Application` с указанным `id` не существует при обновлении или удалении, THEN THE Storage SHALL возвращать ошибку `StorageError::NotFound`.
7. THE Storage SHALL создавать таблицу `applications` при инициализации, если она не существует.

### Requirement 4: CLI-интерфейс для управления заявками

**User Story:** Как пользователь, я хочу управлять заявками через командную строку, чтобы добавлять, просматривать и обновлять их статус.

#### Acceptance Criteria

1. WHEN пользователь выполняет команду `job-notifier add-application --company <name> --position <pos>`, THE CLI SHALL создавать новую запись `Application` со статусом `Submitted` и сроком ожидания 21 день.
2. WHERE пользователь указывает флаг `--reply-days <n>`, THE CLI SHALL устанавливать `expected_reply_days` равным `n` вместо значения по умолчанию.
3. WHERE пользователь указывает флаг `--notes <text>`, THE CLI SHALL сохранять текст в поле `notes` записи.
4. WHEN пользователь выполняет команду `job-notifier list-applications`, THE CLI SHALL выводить все записи `Application` в табличном формате с колонками: ID, компания, позиция, дата подачи, дедлайн, статус.
5. WHEN пользователь выполняет команду `job-notifier update-status --id <id> --status <status>`, THE CLI SHALL обновлять поле `status` записи с указанным `id`.
6. IF пользователь передаёт недопустимое значение `--status`, THEN THE CLI SHALL выводить сообщение об ошибке с перечислением допустимых значений: `submitted`, `in-review`, `rejected`, `offer-received`, `withdrawn`.
7. WHEN пользователь выполняет команду `job-notifier delete-application --id <id>`, THE CLI SHALL удалять запись с указанным `id` и выводить подтверждение.

---

### Requirement 5: Уведомления об истечении срока ожидания

**User Story:** Как пользователь, я хочу получать уведомление в день истечения срока ожидания ответа от компании, чтобы своевременно принять решение о дальнейших действиях.

#### Acceptance Criteria

1. WHEN Scheduler выполняет плановый запуск, THE Scheduler SHALL проверять наличие записей `Application`, у которых дедлайн совпадает с текущей датой.
2. WHEN найдены записи `Application` с истёкшим дедлайном, THE Notifier SHALL отправлять уведомление с указанием компании, позиции и даты дедлайна для каждой такой записи.
3. THE Notifier SHALL форматировать уведомление об истечении дедлайна отдельно от уведомлений о новых вакансиях.
4. WHILE статус записи `Application` равен `Rejected`, `OfferReceived` или `Withdrawn`, THE Scheduler SHALL пропускать эту запись при проверке дедлайнов.
5. THE Scheduler SHALL выполнять проверку дедлайнов при каждом плановом запуске, включая запуск через флаг `--run-once`.

---

### Requirement 6: Совместимость и нефункциональные требования

**User Story:** Как разработчик, я хочу, чтобы новые компоненты органично вписывались в существующую архитектуру проекта, чтобы не нарушать работающий код.

#### Acceptance Criteria

1. THE Universal_Scraper SHALL реализовывать трейт `Scraper` из `src/scraper/mod.rs` без изменения сигнатуры трейта.
2. THE Application_Tracker SHALL использовать существующий `SqliteStorage` и расширять его новыми методами, не изменяя существующих.
3. THE Storage SHALL расширять трейт `Storage` новыми методами для работы с `Application`, сохраняя обратную совместимость с существующими методами.
4. WHEN компилируется проект с новыми компонентами, THE проект SHALL компилироваться без ошибок и предупреждений.
5. THE Universal_Scraper SHALL корректно обрабатывать HTML-страницы с кириллическим текстом (UTF-8).
